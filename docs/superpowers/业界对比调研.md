  二、Parrot 与各框架维度对比

  2.1 引擎架构

  ┌────────────┬────────────────────────────────────────┬────────────────────────────────┬────────────────────────┬───────────────────────┐
  │    维度    │                 Parrot                 │           Google ADK           │       OpenAI SDK       │       Codex CLI       │
  ├────────────┼────────────────────────────────────────┼────────────────────────────────┼────────────────────────┼───────────────────────┤
  │ 循环模式   │ ReAct (固定 20 轮)                     │ Flexible multi-agent graphs    │ ReAct + handoffs       │ Multi-turn agent loop │
  ├────────────┼────────────────────────────────────────┼────────────────────────────────┼────────────────────────┼───────────────────────┤
  │ 流式       │ SSE → ProviderStreamEvent → AgentEvent │ Event-driven ask-produce       │ Runner.run_streamed    │ SSE with compact      │
  ├────────────┼────────────────────────────────────────┼────────────────────────────────┼────────────────────────┼───────────────────────┤
  │ 中断       │ tokio::select! + Abort                 │ 原生支持                       │ Pause/resume via state │ 原生支持              │
  ├────────────┼────────────────────────────────────────┼────────────────────────────────┼────────────────────────┼───────────────────────┤
  │ 状态持久化 │ EventLog JSONL + snapshot              │ SessionService + MemoryService │ SQLite/Redis Session   │ SQLite + snapshot     │
  └────────────┴────────────────────────────────────────┴────────────────────────────────┴────────────────────────┴───────────────────────┘

  可借鉴点：

  1. ReAct 迭代上限可配置化 — 当前 MAX_REACT_ITERATIONS 是硬编码 20。ADK 和 Codex 都支持按模型/task 动态调整上限，避免简单任务等 20 轮才超限。
  2. Google ADK 的 Plugin 系统 — 允许全局拦截 agent / tool / LLM 行为（类似中间件）。Parrot 目前无此抽象，retry、logging、context filter 都是硬编码。可考虑在 engine 管线中加 hook point：
  请求 → [plugins...] → Provider call → [plugins...] → Tool dispatch → [plugins...]
  2. 这意味着 ProviderStreamEvent 流的两端都可以插入横切逻辑。
  3. OpenAI SDK 的 Harness/Sandbox 分离 — 将"决定做什么"与"实际执行"物理隔离，sandbox 不持有凭证。Parrot 当前所有工具都在 daemon 进程内执行。如需隔离执行 shell 等危险操作，可参考此模式（或许用 job objects /
  containers）。

  2.2 工具系统

  ┌──────────┬──────────────────────────┬──────────────────────────┬────────────────────────┬───────────────────────────┐
  │   维度   │          Parrot          │        Google ADK        │       OpenAI SDK       │         Pi Agent          │
  ├──────────┼──────────────────────────┼──────────────────────────┼────────────────────────┼───────────────────────────┤
  │ 注册方式 │ ToolRegistry::register() │ Function-as-tool         │ @function_tool 装饰器  │ Capability-gated hostcall │
  ├──────────┼──────────────────────────┼──────────────────────────┼────────────────────────┼───────────────────────────┤
  │ 确认流   │ ConfirmConfig + router   │ RequireConfirmation flag │ needs_approval on tool │ Command mediation         │
  ├──────────┼──────────────────────────┼──────────────────────────┼────────────────────────┼───────────────────────────┤
  │ 工具数   │ 7 个                     │ 不限                     │ 不限                   │ 8 个（可扩展）            │
  ├──────────┼──────────────────────────┼──────────────────────────┼────────────────────────┼───────────────────────────┤
  │ MCP 支持 │ Phase 2 规划             │ 原生 MCP client          │ —                      │ 内置 MCP 支持             │
  └──────────┴──────────────────────────┴──────────────────────────┴────────────────────────┴───────────────────────────┘

  可借鉴点：

  4. MCP 工具聚合模式 — 当前业界趋势是用少量通用工具（"verbs"）+ 按需发现具体工具（"nouns"），而非注册几十个扁平工具。Google ADK 的 SkillToolset 通过 3 级渐进式加载（L1 元数据 → L2 指令 → L3 资源）减少 baseline
  context 90%。

  4. 对 Parrot 的启示：MCP 实现时可设计为工具组（toolset），每组有元数据描述，引擎仅在相关时加载该组的 schema，避免把几十个工具的 JSON schema 全部塞进 system prompt。
  5. Pi Agent 的安全模型 — 对 Parrot 的 shell / file_write 工具有参考价值：
    - Capability gate：显式的能力开关
    - Command mediation：在执行前检查危险模式（如 rm -rf /、reverse shell）
    - Tamper-evident risk ledger：可审计的执行记录

  当前 Parrot 的 shell 工具通过 shell_allowed 配置控制，可以加一层命令白名单/黑名单 mediation。

  ---
  2.3 上下文管理

  ┌─────────────┬─────────────────────────────┬─────────────────────┬───────────────────────┐
  │    维度     │           Parrot            │     Google ADK      │       Codex CLI       │
  ├─────────────┼─────────────────────────────┼─────────────────────┼───────────────────────┤
  │ 裁剪策略    │ 按完整轮次删除 + token 估算 │ Mem service 分层    │ Compaction API (摘要) │
  ├─────────────┼─────────────────────────────┼─────────────────────┼───────────────────────┤
  │ Token 估算  │ 简单 /4                     │ 精确 tiktoken       │ 精确                  │
  ├─────────────┼─────────────────────────────┼─────────────────────┼───────────────────────┤
  │ 系统 prompt │ 固定注入 context[0]         │ SkillToolset 渐进式 │ AGENTS.md 文件系统    │
  └─────────────┴─────────────────────────────┴─────────────────────┴───────────────────────┘

  可借鉴点：

  6. Compaction 替代纯裁剪 — Parrot 当前超出 token 限制时直接删除旧轮次。Codex CLI 和 Claude Code 的做法是调用 LLM 做 compaction（摘要），保留语义连续性而不是丢弃信息。Codex 有专门的 /responses/compact
  API。Parrot 可以在 context 裁剪前先尝试 compaction，失败再 fallback 到硬裁剪。
  7. Codex 的双层 memory 模型 — 极低成本实现持久记忆：
    - L1: AGENTS.md（静态，用户维护，filesystem-based）
    - L2: memories/（自动生成，后台合并，超时淘汰）

  Parrot 可借鉴：在 daemon 空闲时自动将近期 session 总结为结构化记忆，存入 data_dir/<session>/memories/，新 session 启动时在 system prompt 注入相关记忆摘要。

  ---
  2.4 事件流 & 持久化

  Parrot 在这方面的设计已经很好——三层嵌套生命周期、PersistedAgentEvent + seq 索引、完整性检查、snapshot 定期落盘。以下几点可增强：

  8. Snapshot 频率自适应 — 当前固定每 100 个事件 snapshot。Codex 的 compaction 在 token 接近上限时触发。Parrot 可以在 context 接近裁剪阈值时自动触发 snapshot，减少不必要 I/O。
  9. Codex 的 Goals 系统 — 跨 session 的任务追踪。Parrot 的 session 是独立的，跨 session 的长期任务（如"重构整个 error handling"）无状态追踪。可以引入 SessionConfig.goal 字段，daemon 在 session 列表里展示
  goal，resume 时自动注入 goal 到 system prompt。

  ---
  2.5 多 Agent / 编排

  Parrot 目前是单 agent 模式。对比：

  ┌────────────┬────────────────────────────────────────────────────────┐
  │    框架    │                     多 Agent 模型                      │
  ├────────────┼────────────────────────────────────────────────────────┤
  │ Google ADK │ Multi-agent execution graphs, hierarchical teams       │
  ├────────────┼────────────────────────────────────────────────────────┤
  │ OpenAI SDK │ Handoffs (transfer_to_<agent>), parallel sub-agents    │
  ├────────────┼────────────────────────────────────────────────────────┤
  │ LangGraph  │ Explicit state-machine graphs with conditional routing │
  ├────────────┼────────────────────────────────────────────────────────┤
  │ CrewAI     │ Role-based sequential/hierarchical processes           │
  └────────────┴────────────────────────────────────────────────────────┘

  可借鉴点（Phase 2/3）：

  10. Subagent 模型 — Claude Code 使用 subagent 做并行探索（code review、research），结果回传主 agent。Google ADK 的并行 sub-agent workers 是一种轻量委派，不需要完整的 graph engine。Parrot 可在 engine 中加一个
  delegate tool，由模型决定是否 spawn 子任务。

  2.7 Crate 架构

  Parrot 的 crate 拆分（当前 feat/crate-split 分支）方向与业界一致：

  ┌─────────────────────┬────────────────────────────────────┐
  │    Parrot crate     │            对应业界概念            │
  ├─────────────────────┼────────────────────────────────────┤
  │ parrot-protocol     │ A2A protocol / ACP                 │
  ├─────────────────────┼────────────────────────────────────┤
  │ parrot-core (trait) │ ADK runtime layer                  │
  ├─────────────────────┼────────────────────────────────────┤
  │ parrot-providers    │ LLM provider plugin                │
  ├─────────────────────┼────────────────────────────────────┤
  │ parrot-tools        │ MCP server / tool plugin           │
  ├─────────────────────┼────────────────────────────────────┤
  │ parrot-daemon       │ App server (类比 Codex app-server) │
  └─────────────────────┴────────────────────────────────────┘

  与其他项目的对比：
  - Codex CLI 也是 Rust workspace，app-server 是 JSON-RPC over stdio
  - Pi Agent 的 crate 更细：单独的 rich_rust（TUI）、asupersync（async runtime）
  - Google ADK 的 plugin 机制比 Parrot 的 trait 抽象多一层中间件

  可借鉴点：

  12. parrot-api crate — 当前 parrot-core 同时包含 trait 定义和引擎实现。随着 providers/tools 增多，可提取纯 trait crate（LlmProvider、Tool、ChatMessage 等），让 providers/tools
  只依赖薄接口而无需编译整个引擎。这在 crate-split 设计文档 §8.4 也有讨论，时机成熟时可做。
  13. Codex 的 app-server 抽象 — 当前 Parrot 的 daemon binary 通过 WS 与 CLI 通信。Codex 的 app-server 是 JSON-RPC over stdio，使得多种前端（VS Code、桌面 app、web）共享同一 agent 核心。Parrot 的 parrot-daemon
  已经接近这个设计，但 run_with() 接口可以更标准化——增加一个 Transport 参数而不是硬编码 WS，就可以支持 stdio、Unix socket 等多种传输方式。

  ---
  四、Parrot 的独特优势（不应丢掉的方向）

  在与上述项目对比中，Parrot 有几个设计决策是其差异化优势，值得保留：

  - Event sourcing 式持久化（JSONL event log + 完整性检查 + snapshot）— Google ADK 和 OpenAI SDK 用传统数据库 session，Parrot 的方式更利于审计、重放、调试
  - IPC 边界强制分离 — daemon + thin client via WS，而非单体 CLI。这比 Codex CLI 的单进程架构更利于扩展到 IM、web 等交互通道
  - Trait-based DI — Tool/Provider 通过 trait + registry 注入，测试可用 mock，这在其他 Rust agent 项目中少见
  - Rust 原生 — 相比 Pi Agent 的 21MB 二进制，Parrot 启动极快，资源占用低，更利于边缘/嵌入式部署

  ---
  总结：Parrot 在核心引擎和持久化方面已经有很好的基础。最有价值的下一步是 context compaction（解决长对话信息丢失）、双层 memory（跨 session 学习）和 engine hook/plugin 点（保持可扩展性）。
